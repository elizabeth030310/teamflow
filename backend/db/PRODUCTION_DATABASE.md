# TeamFlow 운영 데이터베이스

## 연결과 권한

- 저장소 루트의 Compose는 로컬 개발용입니다. PostgreSQL 포트는 `127.0.0.1`에만 게시합니다. 운영 DB는 앱과 승인된 관리 작업만 접근할 수 있는 비공개 네트워크에 둡니다.
- 백엔드는 `SPRING_PROFILES_ACTIVE=prod`로 실행합니다. `TEAMFLOW_PROD_DB_HOST`, `TEAMFLOW_PROD_DB_NAME`, `TEAMFLOW_PROD_DB_USER`, `TEAMFLOW_PROD_DB_PASSWORD`, `TEAMFLOW_PROD_DB_SSL_ROOT_CERT`를 운영 환경에서 공급합니다. DB 포트 기본값은 5432이며 필요하면 `TEAMFLOW_PROD_DB_PORT`를 사용합니다. CA 파일은 앱 실행 계정에서 읽을 수 있도록 마운트하고, 접속 호스트는 인증서와 일치시킵니다. JDBC는 `sslmode=verify-full`을 사용합니다.
- 마이그레이션 실행 계정과 앱 계정을 분리합니다. 앱 계정에는 슈퍼유저·스키마 소유권·DDL·역할 부여 권한을 주지 않습니다. 실제 앱 쿼리에 필요한 테이블별 조회·쓰기와 시퀀스 사용만 부여합니다. `users`의 삽입·수정 권한은 열 단위로 부여하고 `role`은 제외합니다. 관리자 감사 테이블에는 조회와 삽입만 허용합니다. 앱 연결로 필요한 동작이 성공하고 권한 밖 DDL 및 역할 변경이 차단되는지 스테이징에서 확인합니다.
- `TEAMFLOW_ATTACHMENT_STORAGE_ROOT`는 비공개 영속 볼륨의 경로로 지정합니다. 운영 프로필은 HTTPS 전용 세션 쿠키를 사용합니다. 프록시는 [요청 보안 배포 안내](../../frontend/README.md#teamflow-요청-보안)를 따릅니다.

## 마이그레이션 적용 순서

1. 배포 대상 커밋과 DB 스키마 기준본을 결정합니다. `backend/db`의 SQL은 기존 테이블을 전제로 한 증분 파일입니다. 빈 DB에는 검토된 스키마 기준본을 먼저 복원합니다. 운영 프로필은 Hibernate 스키마 검증만 수행하고 자동으로 변경하지 않습니다.
2. DB와 첨부파일을 기록한 같은 복구 지점에서 스테이징으로 복원합니다. 현재 스키마와 적용 이력을 비교해 누락된 SQL만 목록화합니다. 역할 스키마 `192-a-8-user-role.sql`을 회원 관리 스키마보다 먼저 적용합니다. 193-D 문서 서식은 193-A 문서 테이블이 선행되어야 합니다.
3. [192-b-member-management-schema.sql](192-b-member-management-schema.sql)은 회원 상태, 세션 버전, 관리자 한 명 제한, 감사 테이블을 준비합니다. 관리자 신원을 만들거나 변경하지 않으며 기존 비공개 관리자 신원 제약도 유지합니다. 관리자 계정이 둘 이상이거나 기존 데이터가 제약과 충돌하면 트랜잭션이 실패합니다. 비공개 192-B가 이미 적용된 환경에서는 스키마 전용 파일을 재적용하기 전에 기존 제약과 감사 테이블 정의를 비교해 필요한 변경만 검토합니다.
4. 마이그레이션 전용 계정으로 승인된 파일을 한 번씩 적용합니다. `psql`을 쓸 경우 `ON_ERROR_STOP=1`을 지정해 오류 후 다음 작업을 중단합니다. 적용 파일명·버전·해시와 성공 여부를 기록합니다. 스테이징에서 `prod` 프로필로 시작해 가입, 로그인, 관리자 감사 조회, 알림, 문서, 첨부 목록과 다운로드를 점검합니다. JDBC로 직접 조회하는 테이블은 Hibernate 검증만으로 확인되지 않습니다.

- 프로젝트 초대 알림을 사용하는 백엔드로 교체하기 전에 [199-project-invitation-notifications.sql](199-project-invitation-notifications.sql)을 적용합니다. 기존 알림 및 멤버십 스키마가 필요합니다. 별도 앱 역할에는 알림의 기존 권한에 더해 `notifications.created_at` 수정 권한이 필요합니다. 기존 대기 초대는 받은 초대 목록에 남고, 첫 재전송 때 알림이 생성됩니다.

## 백업과 복구 검증

- 목표 복구 시간과 허용 가능한 데이터 손실 시간에 맞춰 DB 백업 주기와 보존 기간을 정합니다. DB 백업과 별도로 첨부파일 볼륨을 암호화해 백업합니다. 복구 지점을 맞추려면 앱의 쓰기 요청과 첨부 정리 작업을 중지한 상태에서 DB와 볼륨의 백업을 확보하고 두 백업의 식별자를 함께 기록합니다.
- 운영에서 분리한 환경에 DB와 첨부 볼륨을 복원합니다. 복원 환경의 SMTP를 비활성화하거나 테스트 전용으로 제한합니다. 앱 전용 계정으로 접속해 주요 테이블 건수, 관리자 감사 기록, 샘플 문서와 첨부파일 다운로드를 확인합니다. 복구 소요 시간, 누락 여부, 확인 결과를 기록합니다.
- 운영 반영은 스테이징 복구와 검증을 통과한 뒤 진행합니다. 마이그레이션 후 문제가 생기면 쓰기를 중지하고 배포 전 DB와 첨부 복구 지점을 함께 사용합니다. 복구 시점 이후에 받은 기록의 손실 가능성을 먼저 판단합니다.
