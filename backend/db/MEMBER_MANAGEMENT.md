# TeamFlow 192-B 회원 관리

## 적용 순서

1. 변경 대상 DB를 백업하고, 192-A 역할 마이그레이션이 적용됐는지 확인합니다. 아직 적용하지 않았다면 `192-a-8-user-role.sql`을 먼저 적용합니다. 기존 DB의 유일한 `ADMIN`이 id 3이고 이메일이 운영 마이그레이션의 관리자 신원 조건과 일치하는지 확인합니다.
2. 백엔드를 중지하고 저장소 루트에서 아래 명령으로 `192-b-member-management.sql`을 적용합니다. 기존 회원은 정상 상태로 시작합니다. 역할이나 계정 상태를 마이그레이션에서 일괄 변경하지 않습니다. 관리자 설정이 지정된 신원과 충돌하면 마이그레이션 전체가 실패합니다. 관리자 계정이 없는 별도 환경에는 자동으로 관리자 계정을 생성하지 않습니다.

   ```powershell
   Get-Content -Raw backend/db/192-b-member-management.sql | docker compose exec -T postgres psql -U teamflow -d teamflow -v ON_ERROR_STOP=1
   ```

3. SQL이 성공하면 백엔드와 프런트엔드를 교체하고 기존 관리자로 로그인합니다. `#/admin`에서 회원 목록과 감사 기록을 조회합니다. 일반 계정은 기존 작업 공간으로 들어갑니다.
4. 정지, 해제, 강제탈퇴는 격리된 환경의 테스트 회원으로 검증합니다. 정지 직전 세션과 재로그인이 모두 거절되는지, 해제 후 새 로그인만 허용되는지, 강제탈퇴 후 협업 기록이 남는지 순서대로 확인합니다. 자동 검증은 백엔드 폴더의 `test-isolated.ps1`로 실행합니다.

## 강제탈퇴와 개인정보

강제탈퇴는 협업 기록과 참조를 유지하는 접근 비활성화입니다. 사용자 행과 연결된 프로젝트, 업무, 댓글, 활동 및 감사 기록이 유지됩니다. 이름, 이메일과 비밀번호 해시도 DB에 남으므로 개인정보 파기나 익명화가 이루어지지 않습니다. 동일 이메일로 재가입할 수 없습니다. 회원 관리 화면에는 이름, 이메일과 계정 상태를 표시하며 자격 증명은 응답에 포함하지 않습니다.

강제탈퇴를 되돌리는 관리자 화면이나 API는 없습니다. 오조치 복구가 필요하면 별도 운영 승인 하에 해당 사용자의 상태 변경, 세션 버전 증가, 복구 감사 기록 삽입을 한 트랜잭션에서 수행합니다. 복구해도 이전 세션은 재활성화되지 않습니다.

감사 기록에는 처리자와 대상의 ID, 이전·이후 상태, 일시, 입력한 사유가 남습니다. 화면은 최근 100건을 조회합니다. 사유에는 민감한 개인정보를 입력하지 않습니다. 자동 보존기간, 파기, 익명화 기능은 구현 범위에 포함되지 않습니다. 보존기간과 개인정보 삭제 요청 처리 절차는 운영 정책에서 별도로 정해야 합니다.
